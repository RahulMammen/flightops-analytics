# FlightOps — Flight Operations Analytics Pipeline

FlightOps is a small, reproducible analytics pipeline over **synthetic** flight operations for a **fictional
airline**. It shows SQL analytics in DuckDB, Parquet outputs, data-quality rules with a quarantine, deduplication,
idempotent ingestion, and record accounting that reconciles exactly.

> **All data is synthetic.** The carrier, the four-letter station codes (NORA, VELM, KRIS, ...), the aircraft
> tails (FX-001 ...) and every timestamp are generated by `src/flightops/generate.py`. None of the numbers below
> describe a real airline, and no operational benefit is claimed.

## Definitions

| Term | Definition |
|---|---|
| Time zone and units | All timestamps are UTC (`YYYY-MM-DD HH:MM`); all durations are in minutes |
| Scheduled flights | Accepted rows, cancelled or not |
| Operated flights | Accepted rows with `cancelled = 0` |
| Departure delay | `actual_dep − sched_dep`; negative means early |
| On-time departure | Delay ≤ 15 min. **Rate = on-time / operated** |
| Cancellation rate | **cancelled / scheduled** |
| Delay percentiles | Continuous quantiles (`quantile_cont`) of departure delay over operated flights |
| Turnaround | For one aircraft, ordered by actual departure: next `actual_dep` − previous `actual_arr`. Counted (`OK`) only if the previous destination equals the next origin and 0 < gap ≤ 240 min |
| Excluded turn pairs | `STATION_MISMATCH`, `NON_POSITIVE_GAP` or `LONG_GROUND_STOP` (> 240 min) |
| Airport filter | Matches a flight if the origin **or** the destination is selected. For turnarounds it matches the turn station |
| Route filter | Exact `ORIG-DEST` |

### Cancellation handling

Cancelled flights (`cancelled = 1`) must have **no** actual times; otherwise the row is rejected with
`CANCELLED_WITH_ACTUALS`. Cancelled flights count in the cancellation-rate denominator. They are excluded from
on-time rates, delay percentiles and turnarounds, and their `dep_delay_min` and `on_time_dep` are NULL. Operated
flights must have both actual times (`MISSING_ACTUALS`).

### Deduplication key

`(flight_number, flight_date, origin)`: the operating flight number on its scheduled UTC date from its departure
station. Within each key, the row from the earliest ingestion batch is kept, with ties broken by the lowest
`record_id`. Later rows go to `duplicates`, together with the kept `record_id` and an `identical_content` flag. A
re-transmission with different values is still removed, but it is counted in
`duplicates_with_differing_content`. Deduplication runs **after** validation, so a defective copy is rejected,
not deduplicated.

### Quality rules (reason codes)

`MISSING_REQUIRED`, `INVALID_TIMESTAMP` (a value is present but is not a real date or time, e.g. `2026-02-30`),
`INVALID_CANCELLED_FLAG`, `UNKNOWN_STATION`, `SAME_ORIGIN_DESTINATION`, `SCHEDULE_INCONSISTENT`,
`MISSING_ACTUALS`, `CANCELLED_WITH_ACTUALS`, `IMPOSSIBLE_DURATION` (actual block outside 15..1080 min),
`DEPARTURE_OUT_OF_WINDOW` (more than 60 min early or 24 h late). Every failing rule is recorded for each row.
Definitions live in `REASON_CODES` in `pipeline.py`.

### Idempotency

- Raw CSVs are **never modified**. `raw_flights` is a copy, tagged with `batch_id` and the source file name.
- A file whose SHA-256 is already in `ingestion_log` is skipped entirely.
- Within a new file, `record_id`s already present are not inserted again (`rows_already_present`).
- `transform` rebuilds every derived table from `raw_flights` with `CREATE OR REPLACE`, so repeated runs produce
  identical tables. Running `python -m flightops.cli all` a second time logged
  `"skipped": true, "reason": "file already ingested"` and left the counts unchanged.

## Architecture

```
generate.py ──► data/raw/flights_raw.csv          (preserved, never modified)
            └─► data/raw/injected_defects.csv      (labels; evaluation only)
                         │
pipeline.ingest ─► raw_flights + ingestion_log      (DuckDB: data/warehouse/flightops.duckdb)
                         │
pipeline.transform ─► stg_flights (parsed + reasons[])
                     ├─► quarantine     (any reason)
                     └─► ranked by dedup key ─► duplicates | flights_clean ─► turnarounds
                         │
export_parquet ─► data/processed/{flights_clean,quarantine,duplicates,turnarounds}.parquet
metrics.py (parameterised SQL) ─► reports/ and app/dashboard.py
```

## Dashboard

- **Sidebar filters:** date range, airports, and routes. The route list narrows to the selected airports.
- **Operations:** KPI row, daily on-time rate, delay histogram, CSV export of the filtered flights.
- **Routes:** on-time rate by route and a full route table with CSV export.
- **Turnarounds:** valid-turn KPIs, a ground-time histogram, counts by status and by station.
- **Data quality:** record accounting, reason counts and definitions, ingestion log, the injected-label check,
  quarantined records, CSV export of the quarantine and of the quality summary.

## Limitations

- The data is synthetic. The delay, cancellation and turn distributions are chosen by hand and are not fitted to
  real operations.
- The network is simple: two hubs, ten spokes and out-and-back rotations, with no crew, weather or slot
  constraints.
- The quality rules target the injected defect types, so the 100% detection result is expected by construction.
- A duplicate's kept row is chosen by ingestion order. There is no field-level conflict resolution.
- The tables are in a single-file DuckDB. There is no concurrent writer, scheduling or orchestration.
